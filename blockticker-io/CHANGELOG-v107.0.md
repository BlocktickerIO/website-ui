# BlockTicker v107.0.0 — Price Alerts 2.0

**Release date:** April 2026
**Type:** Feature release + bugfix (additive, one schedule name fix)
**Upgrade path:** Drop-in over v106.0.0

---

## Overview

The existing price alerts system (v50-era code in `class-portfolio.php`) has been
substantially extended. Four new capabilities: **webhook delivery**, **forex pair
alerts**, **repeating alerts**, and a **token-based management UI**. All alert
activity is now logged to `wp_bt_events` for auditability.

Also fixes a `fxlm_fifteen_minutes` schedule name that survived the v100
rename — the `bt_check_price_alerts` cron was incorrectly using the old name.

---

## Bugfix: `fxlm_fifteen_minutes` → `bt_fifteen_minutes`

`class-portfolio.php` lines 25 and 33 were scheduling `bt_check_price_alerts`
with `fxlm_fifteen_minutes`. This works because the old name is still registered
(removed in v103), but it's semantically incorrect. Fixed to `bt_fifteen_minutes`.

## Updated: `class-portfolio.php` — alert methods rewritten

Three methods replaced / added; shortcode registration updated.

### Alert object (extended)

New fields added to every alert stored in `bt_price_alerts`:

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | `md5(email+coin_id+target+time)` — unique per alert |
| `asset_type` | string | `'crypto'` or `'forex'` (auto-detected from `coin_id`) |
| `webhook_url` | string | Optional — POSTed with JSON payload on trigger |
| `repeat_max` | int | Max re-fires: `0` = once, `2`/`5`/`99` = repeat N times |
| `repeat_count` | int | How many times this alert has fired so far |
| `token` | string | 24-char random token — links user to their alert manager page |
| `fired_at` | int|null | Unix timestamp of last fire |

### `sc_price_alerts()` — extended

- Dropdown now includes **forex pairs** (EUR/USD, GBP/USD etc.) from `bt_forex_data`
  in a separate `<optgroup>` — toggled via `show_forex="1"` attribute (default on)
- New **Webhook URL** input field (optional)
- New **Repeat** selector: Fire once / Repeat 2× / Repeat 5× / Always
- Confirmation email now contains a **management link** with the alert token
- Current price display updates live when the asset dropdown changes

### `sc_alert_manager()` — new (`[bt_alert_manager]`)

Token-based alert management page. Read the token from `?bt_alert_token=TOKEN`
in the URL (set by the confirmation email link). Renders a table of the user's
active alerts with:
- Asset, condition, target price, repeat count, time since last fire
- **Delete** button per row (nonce-protected, `?bt_delete_alert=ID`)

No login required — the 24-char random token is the authentication.

### `ajax_save_alert()` — extended

- Validates webhook URL with `esc_url_raw`
- Stores all new fields in the alert object
- Rate limit is now based on **active unfired alerts** (not a transient counter)
  — prevents blocking users who set, fire, and want to set new alerts
- Confirmation email includes the management link

### `check_and_send_alerts()` — extended

**Webhook delivery:** When `webhook_url` is set and the alert triggers, a
non-blocking `wp_remote_post()` sends a JSON payload:

```json
{
  "event":     "price_alert",
  "symbol":    "BTC",
  "direction": "above",
  "target":    70000,
  "current":   70234.5,
  "fired_at":  "2026-04-21T14:00:00+00:00",
  "site":      "BlockTicker"
}
```

**Forex price lookup:** `bt_forex_data` option is read alongside `bt_crypto_data`,
so forex pair alerts are evaluated on every 15-minute check.

**Repeating alerts:** After a repeat alert fires:
- The alert is marked `fired = true` with the timestamp.
- On the next check cycle, if the price has moved *away* from the threshold,
  `fired` is reset to `false` so it can trigger again.
- A 15-minute cooldown prevents the same trigger from firing twice in one cycle.
- `repeat_count` increments on each fire; when it exceeds `repeat_max`, the alert
  is marked exhausted and cleaned up after 30 days.

**`wp_bt_events` logging:** Every triggered alert calls
`BT_Database::log_event( 'PRICE_ALERT', $symbol, $payload )`, populating the
event stream table (designed for this since v96.2 but never written to by alerts).

**Cleanup:** Fired one-shot alerts are retained for 30 days (was 7 days).
Exhausted repeating alerts are also retained for 30 days for audit purposes.
